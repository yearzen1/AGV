```
┌─ Vue3 + Element Plus + Three.js + ECharts（前端）
│    登录/角色菜单 / 参数面板 / 3D 仿真场景 / 实验报表

     ├─ 指标统计：完成时间、总路径长、等待时间、冲突次数
     └─ MySQL（用户、数字字典、路网、任务、实验记录、指标）
```

**代码分层**（与论文"系统设计"章节一致，三目录物理隔离）：

```

agv-backend/     SpringBoot，只做 IO 与编排（Controller / Service / Repository / WebSocket）
agv-frontend/    Vite + Vue3 + TS（视图 / 3D 渲染 / WebSocket 客户端）
```

算法全部在 `agv-algorithm` 实现，`agv-backend` 不得出现算法逻辑——这条是答辩时说"算法可单测"的依据。

### 现实系统分层与本系统定位（写入论文"系统定位/系统边界"）

```
WMS / WCS（仓库管理系统：订单、库存、出入库）
   ↓
Fleet Manager / 中央调度（任务分配、全局路径规划、路口与区域路权）
   ↓ VDA5050 等标准通信协议
车端控制器（执行既定路径 + 激光雷达/防撞条等传感器安全避障）
```

- **本系统模拟的是中间层（中央调度）**：任务分配（就近/贪心）、图上 A* 全局路径规划、时间窗冲突消解——对应现实中的 Siemens SIMOVE、Omron WCS、MHP FleetExecuter 等车队管理产品。
- **本系统不模拟车端传感安全层**：传感器应对的是地图外未知突发障碍，属设备固件与安全认证范畴（ISO 3691-4），不在调度研究范围内。
- **现实同样以集中式调度为主流**：现有 AGV 系统及主流厂商方案"几乎全部采用某种形式的集中控制，由一个中央控制器控制整个车队"（Cardarelli et al., Mechatronics 2017，转述自 Digani et al., ICRA 2014），故本项目采用集中式架构具有现实依据。
- 论文答辩口径："我做的是中枢调度层（多车互避的交通管理层），车端传感避障是另一层，不在本文范围。"

### 仿真对象与被仿真关系（写入论文"系统定位"，答辩必问"你在仿真什么"）

| | 是什么 | 在本项目里 |
|---|---|---|
| **被仿真的（车间/物理世界）** | 路网、货架、AGV 的移动、时间流逝、堵车死锁 | 拓扑路网（节点+路段）+ 离散 tick 推进 + 时间窗冲突 + 指标统计 |
| **真实运行的（调度软件）** | 图上 A*、任务分配、避障决策——本就是代码 | Java 算法包，与现实车队管理系统（FMS）里跑的是同一类东西 |

调度本身是纯计算，恰恰因为如此才需要仿真——**本系统仿真的是调度算法的运行环境（车间与车队），调度算法本身是真实运行的代码**。类比飞行模拟器：被仿真的是空气动力学与飞机，控制律是真实运行的。

**为什么非仿不可**（毕设意义，亦是创新点 3 的根基）：
1. 无真车真仓库——真跑一次需要数十万设备与场地；
2. 对比实验需要：同一路网、同一任务集换算法重跑，现实一次要数天，仿真数秒，且固定随机种子可复现；
3. 算法试错零成本：死锁、撞车在仿真中只是重启，真车会撞。

**答辩一句话口径**："本系统仿真的是 AGV 调度的运行环境（车间与车队），调度算法本身是真实运行的代码；仿真的价值在于让算法可以在零成本、可复现的条件下做对比实验。"

## 三、关键技术决策

### 3.1 拓扑路网与 A*

- 路网唯一真源是 `nodes[] + edges[]`。节点分 `WORKSTATION / CHARGER / BUFFER / JUNCTION`；路段带 `length / direction(单向|双向) / speed / capacity`。
- 加载时把双向边拆成两条有向弧（`E1+` / `E1-`），用邻接表 `Map<NodeId, List<Arc>>` 存储。
- **搜索状态 `(nodeId, inArcId)`**：因为 `g` 含转弯惩罚，代价依赖"从哪条弧来"，closed set 必须按二元组去重；只按 `nodeId` 关闭会得到次优路径且不可复现。
  - 起点：`inArcId = null`；目标：`nodeId == goalId`（不限定入边）。
  - `g = Σ(length / speed) + 转弯惩罚`，转弯惩罚在入弧与出弧夹角超过 45° 时累加。
  - `h = 欧氏距离(node, goal) / vmax`，与入边无关，满足可采纳性（忽略转弯惩罚只会低估）。
- 转弯惩罚必须同时作用于仿真引擎（小车过弯实际减速），否则指标里的"总路径长/完成时间"与规划代价不一致。
- **Dijkstra 降级**：不实现界面与报表，只在 A* 单测里作为等权图的 sanity check（路径长度需一致）。

### 3.2 冲突与消解：逐段滚动预约

**资源与占用**：`Map<NodeId, List<Interval>>`、`Map<ArcId, List<Interval>>`。资源释放即区间过期，不需要显式解锁。

**与初版设计的关键差异（实测后修正）**：
- **节点容量设为 2**，允许路口会车。容量 1 时双向车道在两车互不相让的场景下无法通过。
- **等待期间释放节点占用**。等待者不持有任何资源，资源持有者只可能是行驶中的车辆；行驶中的车辆必然在有限时间内抵达端点并释放，因此结构上不存在资源等待环。早期版本让等待车辆继续占用节点，5 台车以上会稳定死锁（20 万 tick 跑不完 20 单），改为等待即释放后 2–8 台车全部可完成。

**预约粒度（核心决策）**：
- 每辆车只预约**前方 1–2 段**（当前弧剩余 + 下一段），不是出发前占满全程。
- 到达节点前申请下一段弧；申请成功即写入占用区间，失败则进入 `WAITING`。
- 等待必须发生在**安全位置**：已到达的节点（优先 BUFFER / CHARGER），不得停在线段中间。
- 等待超时（默认 30 tick = 3 s）后，带 `(node, time)` / `(edge, time)` 禁行约束**重规划**；连续失败两次进入随机退避。

**三类冲突**（只做这三类，其余不讨论）：

| 类型 | 判定 | 消解 |
|---|---|---|
| 节点冲突 | 两车同一时刻申请同一节点 | 后到者等待，先到者持有节点锁至驶离 |
| 相向冲突 | 同一物理边的正反两条弧被同时占用 | 边级预约：先申请者独占整条物理边，后者等待 |
| 追尾冲突 | 同弧同向两车间距 < `safetyGap`（默认 1.0 m） | 后车降速跟随，间距不足则停车 |

**死锁**：等待环检测（等待图找环）。检出环后，环上 ID 最小的车强制延长等待 + 随机退避一档；超过 3 次仍成环则整条物理边临时 `blocked` 一个窗口并重规划。

### 3.3 WebSocket 帧协议

后端每 100 ms 推一帧：

```json
{
  "tick": 128,
  "agvs": [
    {"id": "AGV-1", "arcId": "E1+", "s": 2.4, "x": 6.1, "y": 5.0,
     "heading": 90.0, "status": "MOVING", "taskId": 7}
  ],
  "events": [
    {"tick": 128, "agvId": "AGV-2", "type": "WAIT_CONFLICT", "arcId": "E3-", "detail": "node J2 occupied"}
  ]
}
```

`s` 是 AGV 在当前弧上已行驶的米数，前端 Three.js 用 `lerp(弧起点, 弧终点, s/length)` 插值。**事件不落库**，只推给前端日志面板。

### 3.4 两种调度算法（对比实验的卖点）

| 算法 | 分配规则 |
|---|---|
| ① Nearest | 任务分配给欧氏距离最近的空闲 AGV |
| ② Greedy-ETA | 用 A* 路径长度 / 速度估计到达时间，分配给预计最早送达的 AGV |

两者**共用同一避障策略、同一预约表实现、同一随机种子、同一任务集**，保证对比公平。任务完成后的空闲行为也一致：回最近 CHARGER 停放，充电位被占则就近 BUFFER 待命。

### 3.5 角色权限

仅两类角色——调度人员（业务操作）、管理员（用户+字典管理）。Spring Security + JWT；菜单按角色渲染，接口层 `@PreAuthorize` 校验；不做细粒度权限。

### 3.6 数字字典

单表 `sys_dict`（`dict_type + dict_code + dict_value`），前端下拉框统一取字典接口。本期只落地 `algorithm`（调度算法类型）与 `metric`（指标名称）两类；`roadnet_template`、`task_type` 先用代码常量。

### 3.7 不做的东西

真实 PLC 对接、移动端、作业人员独立角色入口、Redis、多楼层/禁行区绘制、编辑器撤销重做与自动布局、Dijkstra 界面、`sim_event` 落库。

## 四、路网 JSON 结构（前后端共用）

```json
{
  "nodes": [
    {"id": "CH1", "x": 2,  "y": 5,  "type": "CHARGER"},
    {"id": "J1",  "x": 8,  "y": 5,  "type": "JUNCTION"},
    {"id": "W1",  "x": 8,  "y": 12, "type": "WORKSTATION"}
  ],
  "edges": [
    {"id": "E1", "from": "CH1", "to": "J1", "length": 6, "direction": "TWO_WAY", "speed": 1.0, "capacity": 1}
  ]
}
```

> 双向边加载时拆成 `E1+` / `E1-` 两条有向弧；障碍不建边，临时障碍把边标记 `blocked=true`；起终点必须是节点，不能是"路段中间"。

### 建图编辑器（M1，第 3 周，2–3 天）

**页面三栏**：左工具栏（节点类型、模式切换、导入/导出/保存）｜中画布｜右属性面板（选中节点或路段时显示属性表单，未选中时显示节点数、边数、总长度与校验结果）。

**四个交互**：

1. **加节点**：选类型（工位/充电位/缓存位/路口）→ 点画布 → 吸附 0.5 m 格点 → 自动编号；
2. **连路段**：进入连线模式 → 依次点起点、终点 → 生成边，默认 `TWO_WAY`、`speed=1.0`、`capacity=1`、`length=欧氏距离`（可手改）；
3. **移动节点**：选择模式下拖动节点，关联路段的 `length` 自动重算；
4. **删除**：选中后按 Delete 键或删除按钮，删节点时级联删关联路段，弹确认框。

> 画布底纹的浅色网格只用于画图对齐，存储的仍然是 `nodes[] / edges[]`，不是栅格地图。

**保存前校验**（前端软提示标红，后端硬拦截，错误信息带 `nodeId/edgeId` 供前端定位高亮）：

| 规则 | 说明 |
|---|---|
| ID 唯一 | 节点、路段各自不重复 |
| 端点存在 | 边的 `from/to` 必须在节点表中 |
| 至少 1 个充电位 | 否则 AGV 没有初始停放位 |
| 图连通 | 任一充电位可达全部工位 |
| 单向边可达 | 不允许"只进不出"的死胡同 |
| 数值合法 | `length > 0`、`speed > 0`、`capacity ≥ 1` |
| 不重复建边 | 同一对节点之间只保留一条路段 |

**接口**：`GET /api/roadnet/list`、`GET /api/roadnet/{id}`、`POST /api/roadnet`、`PUT /api/roadnet/{id}`、`POST /api/roadnet/import`、`GET /api/roadnet/{id}/export`。整张图存为一个 `roadnet_json`，不按节点/边拆表。

**验收门（第 3 周末，硬止损）**：必须达到"能加节点、能连边、能保存（含导入导出）"三条。任一不达标 → 立即降级为"模板 + JSON 导入"，第 4 周起零投入，不再回头补。

**不做**：撤销/重做、正交走线、自动布局、多楼层、禁行区绘制、路段中间设点。

### 为什么用拓扑路网而不是栅格

- 工业 AGV 沿固定车道行驶，路段本身有方向、速度、容量，拓扑图能直接表达；栅格把车道压成等距格子，表达不了单向车道与路段容量。
- 栅格分辨率与内存、搜索量矛盾；四邻域路径呈锯齿，3D 里也不像真实车间。
- 栅格把"路口"隐式藏在格子里，冲突只能按格子判；拓扑图把路口建成 `JUNCTION` 节点，节点/路段时间窗可以直接落位。
- [8] 指出"离散化 + 自由转向"的环境在真实双向布局中容易死锁；边级预约 + 等待环检测更贴近真实车队管理。栅格仅保留为 [3] 的对比基线。

> 关联要点：`experiment.create_user` 支撑"查看本人历史实验"；路网/任务集加 `create_user` 便于归属管理。

## 六、指标口径（冻结，论文实验章直接引用）

| 指标 | 定义 | 单位 |
|---|---|---|
| `makespan` | 最后一个任务完成的 tick − 仿真开始 tick | tick（1 tick = 100 ms） |
| `total_path_len` | 全部 AGV 实走弧长之和，**含空驶**（去取货、回充电位） | m |
| `total_wait_tick` | 处于 `WAITING` 状态的 (车 × tick) 之和，**不含无任务空闲** | tick |
| `conflict_count` | "预约失败导致停车"的事件次数，同一次连续等待 N tick 记 1 次 | 次 |

三条补充规则：
1. 空驶路径计入 `total_path_len`，但不单独计入 `makespan`（makespan 只看任务完成时刻）；
2. 等待时间只统计冲突导致的等待，充电/装卸的固定耗时单列为 `service_tick`（不进对比表，避免口径混淆）；
3. 所有对比实验使用同一 seed 生成的任务顺序，seed 随实验记录入库，可复现。

## 十、风险与对策

| 风险 | 对策 |
|---|---|
| 多车死锁导致演示卡死 | 逐段滚动预约 + 边级预约 + 等待环检测；等待随机退避 + 超时强制重规划；固定随机种子保证可复现 |

| WebSocket 同步调试耗时 | W2 先用纯前端假数据打透渲染，W6 再接后端 |
| 论文来不及 | W1 起每周固定产出；实现章边做边写；W6/W9/W10 三次自查兜住重复率 |
