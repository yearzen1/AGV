# 领域模型说明

> 本文解释「为什么这样建模」。术语定义、代码对映和约束以 [领域模型与术语](../reference/领域模型与术语.md) 为准。
> 读者是想改代码、写论文或做答辩的人，不需要先读实现。

## 1. 问题背景

系统要解决的是：在一张车间拓扑路网上，让多台 AGV 完成一批搬运任务，并能对比两种调度策略的效果。

这三个目标决定了模型的重心：

- **路网必须是唯一真源**：编辑器、校验器、A*、仿真、3D 预览都读同一张图。
- **任务必须和路网绑定**：节点编号只在单图内唯一，跨图复用会让「W1」指向不同地点。
- **实验必须可复现**：同一路网、任务集、算法和种子，换一次运行要得到同样结果。

所以模型不是按「数据库表」切的，而是按这三个一致性边界切的。

## 2. 为什么 `RoadNet` 是核心聚合

`RoadNet` 把节点、物理路段和拆好的有向弧收在一起，构造后不可变。这样做的原因：

- **不变量集中**：编号唯一、端点存在、缓存位叶子、充电位可达工位等规则都在保存前一次校验，而不是散落在各个服务里。
- **算法不需要理解编辑器**：A*、预约表、仿真只依赖 `RoadNet`，不关心前端画布、模板、草稿。
- **3D 和 2D 共用同一份数据**：编辑器和 `RoadNetScene` 都消费 `RoadNetPayload`，避免两套坐标或两套方向逻辑。

`RoadNet` 构造时故意不做校验，校验放在 `RoadNetValidator`。这是有意的取舍：加载历史数据、单测构造临时图时可以先建图再决定是否校验；保存入口统一调用校验器。

## 3. 为什么物理路段和有向弧要分两层

编辑器里用户画的是「两个节点之间的一条路」，它是无向的；算法需要的是「从 A 到 B 的一条有向通道」。如果只保留一层，会出现两个问题：

- 双向路段在 A* 里要么被当成两条边，要么每次搜索都临时判断方向，重复逻辑。
- 预约表按「弧」登记。双向路段如果共用一条弧，对向车会被误判为同一资源；如果拆成两条，才能同时各走一辆（双车道）或按物理路段互斥（单车道双向）。

因此：

- `NetEdge` 是**物理路段**，保存方向、速度、容量、车道。
- `Arc` 是**算法单位**，双向边拆成 `E1+` / `E1-`，单向边只有一条。
- 边级冲突、单车道互斥仍按 `edgeId` 判定，弧级预约按 `Arc.id` 登记。

这样编辑器只维护一张物理图，算法层拿到的是可直接搜索的有向图。

## 4. 为什么任务集必须绑定一张路网

节点编号是用户可读的短编号（`W1`、`J2`），不是全局 ID。两张图都可能有 `W1`，但位置和连通性不同。

如果任务集不绑定路网：

- 保存时无法判断 `W1` 是否存在、是不是工位。
- 仿真时可能把任务分配到另一张图的同名节点。
- 删除路网时无法判断是否还有任务引用。

所以 `TaskSet.mapId` 是聚合的一部分，并在三个地方强制：

1. 保存任务集时校验端点存在、类型、不同、可达。
2. 启动仿真/实验时校验任务集的 `mapId` 与请求的 `mapId` 一致。
3. 删除路网时统计引用，有引用就拒绝。

## 5. 为什么用逐段滚动预约

预约表记录「某资源在 `[start, end)` 被某台 AGV 占用」。AGV 只有**进入一条弧**时才登记，而不是出发前预约全程。

这样做的好处：

- 路径不需要在出发时完全锁死，前车走了后车可以跟进。
- 等待自然发生在节点上，和现实中的「在路口等」一致。
- 单条弧的预约开销小，适合每个 tick 推进。

代价：

- 局部最优不保证全局最优，可能出现在环上互等的死锁。
- 需要额外机制：连续等待超过阈值触发重规划，检测到等待环时强制打破。

这就是 `waitTimeoutTicks` 和 `DEADLOCK_BREAK` 存在的原因。它们不是补丁，而是逐段预约这个选择的必要配套。

## 6. 为什么调度策略做成策略接口

论文要对比「就近分配」和「贪心 ETA」。如果把算法写死在仿真引擎里，对比实验就得复制引擎。

因此：

- `TaskAssigner` 只暴露「从候选任务里选一条」。
- `NearestAssigner` 用欧氏距离，`GreedyEtaAssigner` 用 A* 估算总时间。
- `TaskAssigners.of(code)` 把字典码映射到实现，仿真引擎只依赖接口。

这样新增策略不需要改引擎；算法包也保持零 Spring 依赖，可以独立单测。

## 7. 为什么实验是独立聚合

一次仿真运行产生很多帧和事件，但真正需要长期保存的只有「实验头 + 四项指标」。

- 实验头记录 `mapId`、`taskSetId`、`algorithm`、`agvCount`、`seed`，保证可复现。
- 指标记录 `makespan`、`totalPathLen`、`totalWaitTick`、`conflictCount`，对应论文实验章。
- 状态机保证 `RUNNING` 最终落到 `FINISHED` / `FAILED` / `ABORTED`，不会永远停在运行中。

事件不落库是同一个取舍：事件频率高、体积大，而论文只需要四项汇总。代价是事后不能回放逐帧过程；如果未来需要回放，应单独设计事件日志，而不是把事件塞进实验表。

## 8. 持久化模型与领域模型的偏差

当前持久化是「整图 JSON + 少量头字段」，不是节点表 + 路段表：

- `warehouse_map.roadnet_json` 保存整张路网。
- `task_set.tasks_json` 保存任务列表。
- `experiment` 与 `experiment_metric` 分表。

原因：

- 路网总是整图读写，拆表不会带来查询收益，反而增加事务和映射成本。
- JSON 让编辑器导入/导出与后端存储保持同一格式。
- 毕业设计规模下，整图写入足够快。

偏差也很明显：

- 实体类叫 `WarehouseMap`，领域叫 `RoadNet`。
- 外键字段叫 `mapId`，领域叫 `roadnetId`。
- 表名 `warehouse_map` 保留了历史命名。

这些偏差不影响运行，但会影响阅读和论文表述。处理方式是**先记录、再分阶段改名**，而不是一次性重命名表、字段和 API。具体步骤见 [如何统一领域命名](../how-to/统一领域命名.md)。

## 9. 模型没有做什么

为避免过度设计，以下 DDD 能力明确不做：

- 不在算法包引入 Repository 接口；算法只接收 `RoadNet` 值对象。
- 不持久化领域事件；`SimEvent` 只用于前端日志。
- 不做 CQRS、事件溯源、聚合快照。
- 不为每个实体建富血模型；校验规则集中在 `RoadNetValidator` / `TaskSetValidator`。

当前规模下，这些能力带来的复杂度大于收益。领域文档的价值在于把「哪些是聚合、哪些是值对象、哪些只是持久化细节」说清楚，而不是把系统改造成完整的 DDD 分层架构。
