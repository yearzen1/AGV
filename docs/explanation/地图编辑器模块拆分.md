# 地图编辑器模块拆分

> 本文解释「为什么把地图编辑器拆成多个模块、边界怎么划」。
> 操作步骤见 [如何编辑车间地图](../how-to/编辑车间地图.md)，术语见 [领域模型与术语](../reference/领域模型与术语.md)。

## 1. 问题背景

地图编辑器最早集中在一个 Vue 单文件组件里：

```text
RoadNetEditor.vue
├── 页面壳：工具栏、画布、侧栏、弹窗
├── 编辑状态：节点、路段、区域、选择、历史
├── 画布交互：缩放、平移、框选、拖动、吸附
├── 编辑命令：新建、拆分、合并、反转、对齐、批量属性
├── 渲染数据：任务流向、图例、小地图、比例尺
└── 导出：PNG、SVG、JSON
```

这个文件在功能增加后超过 3500 行。问题不是「行数多」本身，而是：

- 改一个交互要同时读模板、样式和十几段状态代码；
- 撤销/重做、脏标记、草稿、导出各自依赖同一组 `ref`，很容易漏改；
- 新增一种画布对象（例如区域）时，必须在同一个文件里同时改选择、历史、渲染、导出和侧栏；
- 纯几何计算和 DOM 交互混在一起，无法单测。

因此拆分的首要目标不是「文件数变多」，而是把**稳定的规则**和**易变的交互**分开。

## 2. 分层与依赖方向

拆分后按三层组织：

```text
components/
  RoadNetEditor.vue             组装层：props/emits、provide、defineExpose
  roadnet/
    editorContext.ts            类型化 provide/inject 上下文
    editorZones.ts              区域纯函数：类型、颜色、归一化、矩形命中
    useRoadNetEditor.ts         编辑状态与命令（当前仍承担较多编辑逻辑）
    components/
      EditorToolbar.vue         工具栏
      EditorCanvas.vue          SVG 画布与悬浮层
      EditorSidePanel.vue       属性/区域/统计/校验
      EditorDialogs.vue         悬浮提示、右键菜单、帮助弹窗
```

依赖方向固定：

```text
editorZones.ts（纯函数）
        ↑
useRoadNetEditor.ts（状态与命令）
        ↑
EditorToolbar / EditorCanvas / EditorSidePanel / EditorDialogs
        ↑
RoadNetEditor.vue（组装）
```

约束：

- `editorZones.ts` 不 import Vue、Element Plus 或页面组件，可以直接用 Node 单测。
- `useRoadNetEditor.ts` 可以 import Vue，但不 import 具体子组件；它是编辑状态的唯一持有者。
- 子组件只通过 `useEditorContext()` 读写状态，不互相直接引用，也不自己新建一份节点/路段数据。
- `RoadNetEditor.vue` 是唯一知道 props / emits / `defineExpose` 的地方，页面 `RoadNetView.vue` 不需要改调用方式。

## 3. 为什么用 EditorContext 而不是层层 props

画布、工具栏、侧栏共享的是同一份编辑状态：当前工具、选择集合、节点/路段/区域、视图变换、历史栈。如果全部用 props/emits 传递，会出现：

- 画布组件需要几十个 props 和十几个 emit；
- 新增一个字段要改三层组件；
- 兄弟组件之间要靠父组件转发事件。

因此用 `provide/inject` 提供一个类型化的 `EditorContext`。当前实现是扁平对象：`nodes`、`edges`、`zones`、`tool`、`selectedNode`、`addNode`、`undo`、`view` 等都在同一层，类型由 `useRoadNetEditor` 的返回值推导：

```ts
export type EditorContext = ReturnType<typeof useRoadNetEditor>
export const EDITOR_KEY: InjectionKey<EditorContext> = Symbol('RoadNetEditor')
```

代价是依赖关系不如 props 直观。为此在 `editorContext.ts` 里集中声明注入键，并要求子组件只通过 `useEditorContext()` 获取，不直接 import `useRoadNetEditor`，避免隐式耦合。

## 4. 哪些留在壳里

`RoadNetEditor.vue` 只保留：

- props / emits 声明；
- 创建并 provide `EditorContext`；
- 组合子组件；
- `defineExpose` 的公开方法。

键盘监听、全屏监听、自动保存定时器等页面级生命周期在 `useRoadNetEditor.ts` 里注册；壳不直接持有编辑状态。

以下内容不放在壳里：

- 节点/路段/区域的几何计算；
- 撤销/重做快照；
- 各类编辑命令；
- 工具栏、画布、侧栏的具体模板和样式。

## 5. 分阶段迁移

一次性移动 3000 行会让 code review 无法判断「是移动还是改行为」。因此分阶段：

1. **基线**：先跑 `type-check`、`build`、`e2e:roadnet`，确认拆分前行为。
2. **纯逻辑**：抽 `types/constants/geometry/model`、历史、导出。
3. **面板与工具栏**：抽侧栏、工具栏、图例、小地图、弹窗。
4. **画布图层**：抽区域/路段/节点/任务图层，画布事件仍集中在一个组件。
5. **功能**：在稳定结构上增加区域注释。

每一阶段都保持 `RoadNetEditor.vue` 的 props、emits、`defineExpose` 和 e2e 依赖的 DOM 类名不变。

当前已完成：`RoadNetEditor.vue` 只剩组装与 `defineExpose`，模板拆成工具栏、画布、侧栏、弹窗四块，区域纯函数独立成 `editorZones.ts`。`useRoadNetEditor.ts` 仍承担选择、节点/路段编辑、历史、视口和导出，后续可以按 `selection` / `nodeEditing` / `edgeEditing` / `history` / `viewport` / `export` 继续拆；拆的时候继续用 e2e 做行为基线。

## 6. 取舍

- **不引入全局 store**：编辑器状态只属于当前页面，放 Pinia 会变成全局单例，切换路网时要手动清理；本地 `provide/inject` 生命周期更清楚。
- **不把画布拆成每个对象一个组件**：节点和路段共享命中、选中、拖动逻辑，拆太细会产生大量事件转发。区域因为交互独立，可以单独一层。
- **不追求每个文件都很小**：优先按职责拆；一个 200 行的 `useEdgeEditing.ts` 比五个 40 行、互相引用的文件更容易维护。
- **纯函数优先**：吸附、矩形、payload 归一化、区域命中这些逻辑没有 DOM 依赖，先做成纯函数并单测，再接 UI。
