# 结构无死锁设计

> 本文解释「为什么单向环能保证不死锁」，以及为什么引擎里那些等待环检测、倒车让行、超时重规划被删掉。
> 术语与代码对映见 [领域模型与术语](../reference/领域模型与术语.md)；编辑操作见 [如何编辑车间地图](../how-to/编辑车间地图.md)。

## 1. 问题背景

多车调度里，死锁的经典成因是同时满足四个条件（Coffman 条件）：

| 条件 | 含义 |
|---|---|
| 互斥 | 一个资源同一时刻只能被一台车占用 |
| 持有并等待 | 车占着已拿到的资源，同时申请下一个 |
| 不可抢占 | 已分配的资源不能被强制收回 |
| 循环等待 | 存在一条「A 等 B、B 等 C、C 等 A」的闭环 |

逐段滚动预约天然满足前三条：车辆进入一条弧时才预约，节点容量默认 1，车不离开节点就不释放预约。第四条一旦由拓扑提供，死锁就成立。

早期版本用「等待环检测 + 倒车让行 + 超时重规划」在运行时打破第四条。这套机制有三个问题：

- **检测不全**：只会把状态为 `WAITING` 且还有剩余路径的车放进等待图。正在装货、停在工位、回充的车仍然持有节点，却不可见，环经过它们就检测不到。
- **打破条件不成立**：倒车让行要求「身后的边和身后的节点都空闲」，而成环的定义就是身后有车，所以这条路径在真死锁时永远失败。
- **判定口径错误**：连续 2000 tick 没有任务完成就判死锁，无法区分真循环等待、重规划抖动和单纯排队过长。

于是改为在**拓扑层**消除第四条：只要路网上不存在「能被占满的有向环」，等待图就不可能成环。

## 2. 四条不变量

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| T1 | 所有路段单向 | 双向边在弧层构成 2-环，两台车即可互等死锁 |
| T2 | 所有节点度数 ≥ 2，没有叶子 | 叶子支路只有一个出入口，进出的两台车必定互等 |
| T3 | 有向图强连通 | 单向化后可能出现「进得去出不来」的区域，车辆永久滞留 |
| T4 | 车队数 < 加权环容量 | 环被占满时形成循环等待 |

前三条由 `RoadNetValidator` 在保存时拦截，第四条在仿真与实验启动时拦截。

### 2.1 为什么双向边必死

一条双向边在算法层拆成 `E1+` 和 `E1-` 两条弧。假设 A 在节点 `u`、B 在节点 `v`，两个节点容量都是 1：

1. A 申请 `u→v`：弧空闲，但目标节点 `v` 被 B 持有，节点容量已满，失败。
2. B 申请 `v→u`：弧空闲，但目标节点 `u` 被 A 持有，失败。
3. 两台车都持有着自己的节点，又都在等对方的节点，形成长度 2 的等待环。

关键点是**节点**而不是车道：即使把这条路改成双车道（两个方向各一条独立弧），节点容量仍是 1，两台车依旧卡在对方的节点上。所以 `LaneMode.DUAL` 只影响通行效率，不影响死锁结论。

### 2.2 为什么叶子支路必死

工位挂在一条支路末端（度数 1），只有一个出入口。A 在支路内装货，B 在支路入口等待进入：

1. A 要出去，需要 B 脚下的入口节点。
2. B 要进去，需要 A 脚下的支路节点。
3. 长度 2 的等待环。

给工位旁再挂一个缓存位不能解决：缓存位本身也是叶子，只是把环从「工位 ↔ 入口」变成「工位 ↔ 缓存位」。只有把工位放到环上，进出才有第二条路。

## 3. 加权环容量

路网上可能有多个有向环。对每个环 `C`，定义

```text
环容量(C) = Σ capacity(v)   （v ∈ C）
加权环容量 minCycleCapacity = min 环容量(C)
车队上限 maxAgvCount = minCycleCapacity − 1
```

节点容量计入公式，是因为充电位通常配置为 4、宽工位可能配置为 2：容量 4 的节点可以停 4 台车，要占满它需要 4 台车。

**车队上限还要受停放位置约束**：所有车在开始和结束都必须停在充电位上，所以充电位容量之和是另一个硬上限。两者取较小值：

```text
车队上限 = min(加权环容量 − 1, 充电位容量之和)
```

**定理**：若路网满足 T1–T3，且 `agvCount ≤ minCycleCapacity − 1`，则任务阶段不可能发生死锁。

**证明**：

1. 假设发生死锁，则等待图上存在环 `A → B → … → A`。每条等待边表示「某车占着节点 `u`，等待节点 `v`」，而 `v` 是它路径上的下一个节点，所以路图上存在有向边 `u → v`。
2. T1 保证方向唯一，该环不会出现「同一条物理边被两个方向各用一次」。
3. 等待环上每台车都占着环上的一个节点，且每个节点都无法再接纳新车辆，说明每个节点都已满，环上至少有 `Σ capacity(v)` 台车。
4. 但 `agvCount < minCycleCapacity ≤ 该环容量`，矛盾。

因此只要拓扑满足不变量，就不需要任何运行时兜底。∎

### 3.1 一个具体例子

标准车间模板是 8 节点单环：

```text
CH1(4) → J1(1) → W1(1) → W2(1) → W3(1) → J2(1) → CH2(4) → J3(1) → CH1
```

只有一个环，环容量 `4+1+1+1+1+1+4+1 = 14`，所以拓扑上限是 13 台。但两个充电位一共只有 `4+4 = 8` 个停放位，因此实际车队上限是 `min(13, 8) = 8` 台，超过 8 台时启动即被拒绝，而不是跑一段时间才死锁。

## 4. 代价

结构保证不是免费的：

- **绕行变长**：单向环上从 `W3` 到 `W1` 要绕几乎一整圈，总里程和单均配送都会上升。
- **无法超车**：环上任何一台车在工位装货，后面的车只能排队。工位容量配成 2 可以把等待的车吸到工位上，减少对环的阻塞，这也是高容量模板存在的理由。
- **路网设计自由度低**：不能画支路、不能画双向巷道；编辑器里「双向」「车道」这两个属性对新图没有意义。

## 5. 为什么现实 AGV 也这么做

Kiva 类仓储机器人采用单向网格：每个格点只允许一个方向，货架站点在网格节点上而不是支路上。这与本文的四条不变量是同一套约束的不同表述。它们能支撑几百台车同场，靠的不是更强的死锁检测，而是**从结构上让死锁无法表达**。

代价同样存在：机器人经常要绕远路。工程上用「多放几个充电位」「站点容量配 2」「动态调整行驶方向」来换回吞吐，而不是放宽拓扑约束。

## 6. 与旧机制的关系

T1–T4 落地后，引擎里以下几段代码在结构上不可达，已删除：

| 旧机制 | 为什么不可达 |
|---|---|
| 工位旁缓存位让位 | T2 没有叶子，且 T1 没有反向弧，「驶入缓存位再回到工位」不可能成立 |
| 倒车让行 | T1 没有反向弧 |
| 等待环检测 | 定理保证等待图无环 |
| 禁行重规划 | 单向单环上不存在替代路径，重规划必然失败 |
| 2000 tick 死锁判定 | 死锁不可发生；`FAILED` 改为表示「未跑完」 |

保留的只有**排队等待**：车仍会因为没有空节点而停住，`WAITING` 状态、冲突计数和等待时长仍然是有效指标，只是不会再形成闭环。
