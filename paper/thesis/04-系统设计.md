# 第 4 章 系统设计

## 4.1 总体架构

系统采用前后端分离的三层结构，并在后端内部把算法与业务进一步解耦。

```
┌─ Vue3 + Element Plus + Three.js + ECharts（前端）
│    登录/角色菜单 / 参数面板 / 3D 仿真场景 / 实验报表
│         ▲ WebSocket（仿真帧推送）   ▼ REST（配置、历史查询）
└─ SpringBoot（后端）
     ├─ 认证授权：JWT + 双角色
     ├─ 仿真编排：引擎驱动、帧推送、实验落库
     ├─ 算法模块：路网模型 / A* / 时间窗 / 调度策略 / 引擎
     └─ MySQL（用户、字典、路网、任务集、实验、指标）
```

代码划分为三个工程：

| 工程 | 职责 | 依赖 |
|---|---|---|
| `agv-algorithm` | 路网模型、校验、A\*、预约表、仿真引擎、调度策略 | 仅 JDK 与 JUnit |
| `agv-backend` | 认证、CRUD、仿真编排、WebSocket、实验持久化 | Spring Boot + 算法包 |
| `agv-frontend` | 界面、三维渲染、图表、实时通信 | Vue 3 生态 |

把算法独立成不依赖 Spring 的模块，一方面便于单元测试与随机化对拍，另一方面也保证了"算法本身是真实运行的代码"这一系统定位——它和真实车队管理系统中的调度内核属于同一类实现。

## 4.2 路网数据结构设计

路网以节点与物理路段为输入，加载后拆分为有向弧。核心结构如下：

| 结构 | 类型 | 说明 |
|---|---|---|
| `NetNode` | 记录 | 编号、坐标、类型（工位/充电位/缓存位/路口）、容量 |
| `NetEdge` | 记录 | 编号、起终点、长度、方向、速度、容量 |
| `Arc` | 记录 | 有向弧，编号为 `edgeId+` 或 `edgeId-`，保留所属物理路段 |
| `RoadNet` | 类 | 节点表、路段表、弧表、出弧邻接表、入弧邻接表、最大速度 |

拆分规则：新路网只允许单向，一条物理路段只生成 `E1+`；历史双向数据仍会生成 `E1-`，用于只读打开与回放，保存时被校验拦截。因此算法层只需处理有向图。

邻接表采用 `Map<NodeId, List<Arc>>`，出弧与入弧各维护一份。出弧用于搜索扩展，入弧用于环容量计算（4.4.5 节）。

## 4.3 路径规划设计

A\* 的搜索状态定义为 `(nodeId, inArcId)`。选择该状态而非裸节点编号的原因在于代价函数包含转弯惩罚：从不同入边到达同一节点，其累计代价与后续转弯代价都不同。若仅按节点关闭，先以较高代价到达的状态可能提前关闭节点，导致最终路径次优。

算法流程如下：

1. 起点状态入队，`g = 0`，`f = h`；
2. 取 `f` 最小的状态，若节点为目标则回溯路径；
3. 否则遍历该节点的出弧，跳过被封锁的路段；
4. 计算新代价 `g' = g + length/speed + turnPenalty`；
5. 若新状态更优则更新并重新入队；
6. 队列为空仍未到达则返回不可达。

启发函数取欧氏距离除以全图最大速度。由于任意路段的实际速度不超过最大速度，且转弯惩罚非负，该函数不会高估真实代价，满足可采纳性与一致性。

## 4.4 冲突消解设计

### 4.4.1 资源模型

系统维护两类可预约资源：

- **节点**：占用区间为 `[到达时刻, ∞)`，直到车辆驶离；容量按节点配置，默认 1；
- **有向弧**：占用区间为 `[进入时刻, 离开时刻+1)`，容量固定为 1。

路网全部单向，一条物理路段只对应一条有向弧，因此弧级预约已经足以保证互斥，不再需要额外的"物理路段占用者"映射。

### 4.4.2 逐段滚动预约

车辆在节点上准备进入下一条弧时，才申请该弧与目标节点的占用。申请失败则进入等待：车留在原地，并保留脚下节点的预约。这一设计有两个直接后果：

1. 等待发生在节点上，不会出现停在路段中间的不安全状态；
2. 严格容量下，等待车辆保留节点预约，资源持有者可能是行驶中的车辆，也可能是等待中的车辆。因此仅靠预约本身不能排除等待环，必须由拓扑约束保证（4.4.4 节）。

### 4.4.3 两类冲突

| 类型 | 判定 | 处理 |
|---|---|---|
| 追尾冲突 | 目标弧的并发占用数已达容量 | 后到者等待 |
| 节点冲突 | 目标节点占用数已达容量 | 后到者等待 |

旧版还有"相向冲突"：双向路段由物理边互斥。改成单向环后，一条边只有一个方向，这一类冲突从模型中消失。

### 4.4.4 结构无死锁

死锁的经典成因是同时满足四个条件（Coffman 条件）：互斥、持有并等待、不可抢占、循环等待。逐段预约天然满足前三条，因此只能在第四条上做文章。

旧版试图在运行时打断循环等待（等待环检测、倒车让行、超时重规划），但这类机制依赖"身后有空位"这个前提，而成环的定义恰恰是身后有车；检测也只能看到状态为等待的车辆，装货与停靠的车不在等待图里。因此改为在拓扑层让循环等待不可表达，要求路网满足三条不变量：

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| T1 | 所有路段单向 | 双向边在弧层构成 2-环，两台车即可互等 |
| T2 | 所有节点度数 ≥ 2，无叶子 | 叶子支路只有一个出入口，进出的两台车必定互等 |
| T3 | 有向图强连通 | 单向化后出现"进得去出不来"的区域，车辆永久滞留 |

三条由路网校验器在保存时拦截。在此基础上可证明：只要车队数小于加权环容量（4.4.5 节），等待图不可能成环。

**证明**：假设发生死锁，则等待图上存在环 `A → B → … → A`。每条等待边表示"某车占着节点 `u`、等待节点 `v`"，而 `v` 是它路径上的下一个节点，故路图上存在有向边 `u → v`；T1 保证方向唯一。环上每个节点都无法再接纳车辆，说明都已满，因此该环上至少有"环上所有节点容量之和"台车。但车队数小于任何一个环的容量和，矛盾。证毕。

该证明的关键在于把"环容量"计入节点容量：容量 4 的充电位要 4 台车才能占满，比容量 1 的节点更难形成闭环。

### 4.4.5 车队上限

加权环容量定义为所有有向环中"环上节点容量之和"的最小值。由于车辆开始和结束都要停在充电位上，充电位还提供了第二个约束：

```text
可停车位(充电位) = capacity − 1
车队上限 = min(加权环容量 − 1, Σ 可停车位)
```

减 1 是给充电位留一个过道位。充电位位于环上，停满会让这个节点变成一堵墙，把整条单环切断，环另一侧的车永远过不去。留出一个空位后，过路车始终可以预约该节点通行。

标准车间环容量 14、可停车位 6，车队上限为 6 台。仿真与实验启动时校验该上限，超出直接返回业务错误 4004，不创建实验。

## 4.5 调度策略设计

两种策略共用同一套避障逻辑，仅在"把任务派给谁"上不同：

- **就近分配**：计算空闲车辆当前位置到任务起点的欧氏距离，取最小者。计算开销为 O(任务数)，不感知路网绕行；
- **贪心 ETA**：用 A\* 分别估计"空驶到起点"与"起点到终点"的耗时，取总耗时最小者。计算开销为 O(任务数 × 寻路)，能感知绕行与单行道。

任务完成后的空闲行为一致：若仍有待分配任务则继续领取，否则返回充电位待命。回充只在"还有过道位"的充电位中选择最近的一个；全部充电位都达到可停车位上限时，才在最近的充电位排队。

## 4.6 数据库设计

系统共 7 张表，实体关系如下：

```
sys_user        用户与角色
sys_dict        数字字典（algorithm / metric）
roadnet         路网（整图存为 JSON）
task_set        任务集（任务列表存为 JSON，绑定路网）
experiment      实验记录（路网、任务集、算法、车辆数、种子、输入快照、创建人）
experiment_metric 实验指标（与 experiment 一对一）
sys_audit_log   业务审计日志（登录、变更、仿真与实验动作）
```

**表 4-1 主要数据表**

| 表名 | 关键字段 | 说明 |
|---|---|---|
| `sys_user` | username、password、real_name、role、status | 密码用 BCrypt 存储 |
| `sys_dict` | dict_type、dict_code、dict_value、sort、status | 算法下拉框数据源（metric 预留） |
| `roadnet` | name、roadnet_json、is_template、create_user | 整图存储，避免节点/边拆表 |
| `task_set` | name、roadnet_id、tasks_json、create_user | 任务列表整体存储，`roadnet_id` 绑定路网 |
| `experiment` | roadnet_id、task_set_id、algorithm、agv_count、seed、status、roadnet_snapshot、taskset_snapshot、create_user | 支撑历史查询与输入回放 |
| `experiment_metric` | experiment_id、makespan、total_path_len、total_wait_tick、conflict_count、avg_delivery_tick | 五项指标 |
| `sys_audit_log` | username、action、target_type、target_id、result、detail、ip、create_time | 只追加，用于追溯谁改了什么 |

各表主键统一为 `BIGINT` 数字类型，由应用侧雪花算法生成，数据库不使用自增列。雪花 ID 取 53 位（41 位毫秒时间戳、2 位实例号、10 位序列），不超过 JavaScript 安全整数，前端可以直接按数字处理；预置模板与演示任务集固定为 `id = 1` 和 `id = 2`，保证论文中的复现参数稳定。

仿真事件不落库。100 ms 粒度的事件若全部持久化，数据量会随仿真时长线性膨胀，而其分析价值有限；因此事件只通过 WebSocket 推送到前端日志面板，落库的仅是实验结束后的汇总指标。

实验记录在创建时把当时的整张路网与任务集 JSON 一并保存为输入快照。只存 `roadnet_id` 时，路网一旦被编辑，历史实验就无法证明"同参数还能得到同结果"；保存输入原文后，回放接口可以直接用快照重跑并比较五项指标，而不必引入地图版本链和"同时只有一版生效"的额外不变量。

## 4.7 接口设计

接口统一以 `/api` 为前缀，返回 `{code, message, data}` 三段结构，`code = 0` 表示成功。鉴权使用 JWT，请求头携带 `Authorization: Bearer <token>`。

**表 4-2 主要接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | 登录并签发令牌 |
| GET | `/api/roadnet/list` | 路网列表 |
| POST/PUT | `/api/roadnet`、`/api/roadnet/{id}` | 新建/保存路网 |
| POST | `/api/roadnet/validate` | 仅校验不落库 |
| GET | `/api/taskset/list`、`/api/taskset/{id}` | 任务集列表（可按 `roadnetId` 过滤）与详情 |
| POST | `/api/sim/start`、`/pause`、`/resume`、`/reset`、`/speed` | 仿真控制 |
| POST | `/api/experiment/compare` | 双算法对比 |
| POST | `/api/experiment/{id}/replay` | 按输入快照重跑并比对五项指标 |
| GET | `/api/experiment/list` | 本人历史实验（分页） |
| GET | `/api/admin/users`、`/api/admin/dict`、`/api/admin/audit` | 管理员接口（审计日志分页） |

返回体中的业务码前三位与 HTTP 状态一致（如 `4040` 对应 `404`、`4012` 对应 `401`），调用方可以同时按状态码和业务码分支处理；未预期的异常只返回通用文案与请求编号，不暴露堆栈。

## 4.8 实时推送设计

后端在启动仿真后为该用户创建一个独立的仿真会话：一份引擎、一条守护调度线程，按 `100 ms / 倍速` 的周期推进。每个 tick 生成一帧，包含全部车辆的快照、本帧事件与实时指标，只通过 `/ws/sim` 推送给发起人的连接。前端收到帧后更新车辆目标位置，渲染循环对位置做线性插值，使离散帧呈现为连续运动。

运行态按用户隔离：一个用户同一时刻只有一个仿真，再次启动只替换自己的会话；不同用户的暂停、倍速、实验 ID 互不影响。线程数量由全局并发上限控制，默认 5 个，超限的启动请求返回 429 而不是继续创建线程。

暂停即跳过推进；调速即重建调度周期；重置则停止该用户的调度器并清空引擎状态。

## 4.9 本章小结

本章给出了系统的总体架构、路网与算法数据结构、冲突消解机制、调度策略、数据库与接口设计，并说明了实时推送的实现方式。其中"等待者不持有资源"的资源模型是保证仿真必然结束的关键设计，第 6 章的规模实验将验证其有效性。
