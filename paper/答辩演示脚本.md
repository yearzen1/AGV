# 答辩演示脚本

> 目标时长 8–10 分钟。引擎不含随机源，同一组参数在任何机器上都会得到相同结果。

## 零、演示前检查（提前 10 分钟）

```powershell
# 1. 后端
cd agv-backend
mvn spring-boot:run

# 2. 前端（另开一个终端）
cd agv-frontend
npm run dev
```

- 打开 <http://localhost:5173>，确认能登录。
- 确认 `agv-backend/data/agvdb.mv.db` 已存在（演示数据已初始化）。
- 关闭无关窗口，浏览器缩放 100%。
- 备用方案：若现场网络或依赖异常，直接使用已构建的 `agv-frontend/dist` 与本机后端。

## 一、管理员视角（约 1.5 分钟）

1. 以 `admin / admin123` 登录。
2. 进入「用户管理」，说明两类角色与启停控制，展示调度人员账号。
3. 进入「数字字典」，选择「调度算法」，把「贪心 ETA」的显示名改一下再改回，说明下拉框由此统一取值。

**讲述要点**：管理员比调度人员多两个菜单；权限在后端 `@PreAuthorize` 上也有校验，不只是前端隐藏。字典只负责显示名、排序与启停，编码与算法实现一一对应，因此页面不开放新增与改编码，避免配置出跑不起来的算法。

## 二、车间地图（约 2 分钟）

1. 切换到 `dispatcher / dispatcher123` 登录。
2. 进入「车间地图」，选择「标准车间（单向环）」，说明 8 节点 / 8 条单向路段、整张图是一个闭环。
3. 点击「另存为」，命名为「答辩演示路网」。
4. 在画布上：
   - 双击一条路段，演示「拆分路段」——在中间插入一个路口，环仍然是环，点「校验」通过；
   - 用「工位」工具在空白处点一个新节点但不连线，点「校验」，展示 `LEAF_NODE` 拦截（叶子支路会让两台车互等）；
   - 删掉这个孤立节点，再点「校验」，恢复通过；
   - 点「保存」。
5. 点「导出 JSON」，说明可批量迁移。

**讲述要点**：画布底纹只是对齐网格，存储的仍是节点与路段，不是栅格地图。保存前后端各校验一次；"全单向、无叶子、强连通"三条不满足就不允许保存，这是结构无死锁的前提。

**兜底**：若现场拖拽不顺，直接演示「套用模板 → 另存为 → 保存」，并说明画布建图在第 3 周即通过验收。

## 三、仿真运行（约 3 分钟）

1. 进入「任务集」，展示「演示任务集（20 单）」，说明起终点在三个工位之间循环。
2. 进入「仿真运行」：
   - 选择标准车间、演示任务集；
   - 算法选「就近分配」，AGV 数量 3；
   - 点「开始」。
3. 观察三维场景：车辆沿路段平滑移动，等待时变红，装卸时变橙。
4. 讲解右侧指标：tick、完成数、完成时间、冲突次数、总里程、总等待。
5. 等待出现 1–2 条「冲突等待」日志，暂停仿真，放大日志面板讲解。
6. 调速到 4x，继续运行至结束。

**讲述要点**：后端每 100 ms 推一帧，前端插值渲染；等待发生在节点上，不会停在路段中间。

**兜底**：若 WebSocket 异常，刷新页面重连；仍不行则切到「对比实验」用离线结果讲解。

## 四、算法对比（约 2.5 分钟）

1. 进入「对比实验」，选择同一路网与任务集，AGV 数量 3。
2. 点「运行对比（两种算法）」。
3. 展示柱状图与表格，读出两组数据：
   - 就近分配：完成时间 2760 tick，冲突 10 次，总里程 803.1 m；
   - 贪心 ETA：完成时间 2668 tick，冲突 5 次，总里程 718.0 m。
4. 切到 AGV 数量 6 再跑一次：就近 2234 tick，贪心 1970 tick，说明规模上去后差距被放大到 11.8%。
5. 下拉到「我的历史实验」，说明按创建人隔离、可回看。

**讲述要点**：同一路网、同一任务集，两个算法共用同一套避障逻辑，因此差异只来自任务分配。单向环上欧氏距离与实际路径严重脱节（W1 到 W3 只隔 16 米，却要绕大半个环），所以用 A\* 估时的贪心 ETA 在 2 至 6 台上全面占优，差距 3.3% 至 20.0%。

**兜底**：现在 6 台是路网允许的上限，现场最多跑到 6 台；填 7 台会被拒绝并提示"该路网最多支持 6 台 AGV"，这本身也是一个可以讲的点。

## 五、难点讲解（约 1 分钟，老师常问）

**问题**：多台车互相等待会死锁，你怎么解决？

**回答要点**：

1. 死锁有四个必要条件：互斥、持有并等待、不可抢占、循环等待。逐段预约天然满足前三条，所以只能在第四条上做。
2. 旧版在运行时打断环：等待环检测、倒车让行、超时重规划。但它有硬伤——倒车要求"身后有空位"，而成环的定义就是身后有车；检测也只看得见等待中的车，装货和停靠的车不在图里。
3. 现在改成拓扑层消除：路网必须全单向、无叶子、强连通。三条由校验器在保存时强制。
4. 在这个前提下可以证明：等待环必然是路网上的一个有向环，环上每个节点都已占满，因此至少要"环上节点容量之和"台车才能形成。只要车队数小于加权环容量，环就占不满，死锁不可达。
5. 车队上限还要看充电位：充电位在环上，停满会把环切断，所以每个充电位留一个过道位。标准车间环容量 14、可停车位 6，上限就是 6 台，超编在启动时直接拒绝。
6. 现场对照：同一套引擎下，旧的双向图在 2 台车时就会互等（论文表 6-5），单向环 1 至 6 台全部完成 20 单（表 6-2）。

## 六、可能的追问

| 问题 | 回答要点 |
|---|---|
| 为什么用拓扑路网不用栅格？ | 车道有方向、限速、容量，栅格表达不了；路口需要显式节点才能做节点级冲突判定 |
| A\* 为什么状态要带入边？ | 代价含转弯惩罚，同一节点从不同来向到达的后续代价不同，只按节点关闭会次优 |
| 时间窗是怎么做的？ | 逐段滚动预约，只占下一段弧与目标节点，节点容量严格约束物理停靠 |
| 你的创新点是什么？ | 可自由建图的环境 + 可证明的结构无死锁 + 统一口径的算法对比报表 |
| 仿真和真实系统的关系？ | 仿的是环境，调度算法是真实代码；对应现实中的 Fleet Manager 层 |
| 单向环会不会绕远？ | 会，这是结构保证的代价；实验里第 6 台车对就近分配已没有收益，只多跑 20.5% 空驶 |
| 为什么不做车端避障？ | 那是设备固件与安全认证范畴（ISO 3691-4），不属于调度层 |
